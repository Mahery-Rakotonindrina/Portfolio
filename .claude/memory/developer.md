## Décisions techniques
- **US-003 (Hero/Sidebar)** : composant réel = `components/Sidebar/index.tsx` (pas de dossier "Hero" séparé). Migré des animations legacy (`fadeInUp`, `letterSpace`, `simpleOpacity`) vers les tokens signature US-002 : `heroBoot`/`heroBootReduced` sur chaque ligne (entrée), parent `MotionStack` avec `staggerChildren` conditionnel (0.1s normal, 0 si `prefers-reduced-motion` via `useReducedMotion()`), `hoverLift`/`hoverLiftReduced` sur le CTA et chaque icône sociale (`whileHover`, valeur passée directement en objet plutôt que par nom de variant — un composant motion ne peut pas combiner un `variants` d'entrée (`initial`/`animate`) et un `whileHover` par nom tirés du même objet si les clés ne correspondent pas : `whileHover={hoverLift.hover}` en objet direct évite le piège).
- Typo scale : remplacé les tailles non-tokenisées (`fontSize="smaller"`, `fontSize="small"`) par les `textStyles` du theme (`hero`, `title`, `label`, `body`) — `textStyle="hero"` appliqué au nom de famille (point focal visuel), `textStyle="label"` (mono, uppercase) au rôle "Développeur Frontend" en gardant le tag `as="h3"` (pas de régression sémantique, juste un style visuel différent).
- Cercle décoratif (`#sidebarCircle`, `components/Sidebar/styles.module.css`) : couleur hardcodée `#97DFFC` remplacée par les tokens du design system via variables CSS Chakra (`var(--chakra-colors-accent-400)` en dark, `var(--chakra-colors-border-subtle)` en light — convention confirmée : un semantic token `border.subtle` génère bien la variable `--chakra-colors-border-subtle`, point remplacé par tiret). Comportement scaleUp (légacy, hors des 5 signatures) conservé tel quel, juste la couleur alignée.
- Sécurité anti-débordement sur le nom de famille (`textStyle="hero"`, 72px à `xl` sur un mot de 14 caractères sans espace dans la colonne Sidebar à 34% de largeur) : `overflowWrap="anywhere"` initial remplacé par une vraie césure typographique après vérification visuelle (capture `screenshots/us003-sidebar-desktop-dark-fixed.png`) qui montrait une coupure moche en plein milieu d'un groupe de lettres ("RAKOTONIND"/"RINA", pas de trait d'union). **Solution retenue** : `lang="fr"` sur le `Text` + `sx={{ hyphens: 'auto', WebkitHyphens: 'auto', msHyphens: 'auto' }}` (propriété `hyphens` hors de la liste des style props Chakra connues → passer par `sx`, pas en prop directe, sinon elle serait silencieusement ignorée) + `overflowWrap="break-word"` en repli uniquement si la césure n'est pas supportée. Résultat vérifié à 1440px (xl) : coupure propre "RAKOTONIN-"/"DRINA" avec trait d'union, plus de débordement ni de casse arbitraire — voir `screenshots/us003-sidebar-desktop-dark-hyphenfix.png` (+ tablette/mobile re-vérifiées sans régression, `*-tablet-dark-hyphenfix.png`/`*-mobile-dark-hyphenfix.png`). La césure navigateur (`hyphens: auto`) fonctionne par patterns phonétiques (algorithme de Liang), pas par dictionnaire — s'applique correctement même à un nom propre absent des dictionnaires standards. Taille `hero`/colonne Sidebar non modifiées, le fix CSS seul a suffi.
- **Méthode de vérification visuelle sans MCP Playwright/chrome-devtools actif** : le CLI `npx playwright screenshot <url> <fichier> --viewport-size "L,H" --wait-for-timeout <ms>` fonctionne de façon autonome (Chromium déjà pré-téléchargé dans le cache local, pas besoin du serveur MCP ni de session redémarrée) — utile pour le developer quand `mcp__playwright__*` n'est pas chargé dans les `tools:` de l'agent ou la session. Capture dans `screenshots/` directement en passant le chemin cible.

- **US-004 (About — Detail + SkillSetModal)** : composants réels = `components/Sections/About/Detail.tsx` (profil + aperçu compétences) et `components/Sections/About/SkillSetModal.tsx` (modal exhaustif). Texte de présentation (bio, tooltip thé/café) conservé caractère pour caractère, seule la présentation visuelle change.

  - **Detail.tsx ne consommait pas `config/skills.ts`** : l'aperçu de compétences (2 colonnes) était une liste d'icônes dupliquée à la main (incluait même `SiGraphql`, absent de `skills.ts`). Remplacé par `Skills.frontend.map(...)` / `Skills.backend.map(...)` directement — plus de drift possible entre l'aperçu et la source de vérité.
  - Couleurs : `useColorModeValue('teal.500', 'cyan.200')` (legacy, pré-US-002) remplacé par `color="accent.default"` partout (Detail + SkillSetModal) — un seul accent, résolu automatiquement par les semantic tokens, pas besoin de `useColorModeValue` au point d'usage.
  - Typo : `textStyle="title"` sur le heading "Ce que je fais.", `textStyle="body"` sur le paragraphe de bio, `textStyle="label"` (mono, uppercase) sur le CTA "Mon attirail de développeur" et sur les intitulés de catégorie du modal (transformation CSS `uppercase` uniquement — texte DOM inchangé). `fontSize="small"`/`"smaller"` (valeurs hors échelle Chakra, même piège que Sidebar US-003) remplacés par `fontSize="sm"` sur les `ListItem`.
  - Animations : `scrollReveal`/`scrollRevealReduced` en cascade (`staggerChildren`, `whileInView` + `viewport={{ once: true, amount: 0.3 }}` sur le `Stack` parent de `Detail` — même mécanique de propagation de variants que `heroBoot`/Sidebar, seul le déclencheur change (`whileInView` au lieu de `animate` au mount). Framer Motion propage l'état animé nommé aux enfants quel que soit le prop qui l'a déclenché (`animate` ou `whileInView`) — pas besoin que chaque enfant redéclare son propre trigger, seul le `variants` suffit. `hoverLift`/`hoverLiftReduced` sur le CTA du modal (objet `.hover` direct, même piège/contournement que Sidebar). `modalEnter`/`modalEnterReduced` câblé sur `SkillSetModal` via la prop `motionProps` de `ModalContent` (`@chakra-ui/react` v2.10) — **découverte** : `ModalContent` accepte `motionProps?: HTMLMotionProps<'section'>`, qui *remplace entièrement* le preset interne (`transitions[preset]` dans `modal-transition.mjs`) dès qu'il est fourni, donc `motionPreset` sur `<Modal>` devient inerte pour le contenu (toujours lu par `ModalOverlay` pour le fondu du backdrop, mais `'none'` est la seule valeur qui change son comportement) — retiré `motionPreset="slideInBottom"` devenu trompeur. Nos tokens `modalEnter`/`modalEnterReduced` ont la forme `{initial, animate, exit}` : passés tels quels en `variants` avec `initial="initial" animate="animate" exit="exit"`, compatible nativement (les noms de clé "initial"/"animate"/"exit" ne sont pas réservés dans un objet `variants`, juste des labels).
  - `ModalContent` restylé avec les jetons `bg.surface`/`border.subtle` + `borderRadius={0}` (cohérent avec l'esthétique "sharp" déjà actée pour `Button variant="outline"` dans Sidebar) plutôt que les couleurs par défaut du thème Chakra.

- **Bugfix post US-003/US-004 : `textStyle` sans effet sur `Heading`/`ModalHeader`** — cause racine identifiée en lisant le code source de `@chakra-ui/system`/`@chakra-ui/styled-system` (`toCSSObject` dans `system.js`, `getWithPriority` dans `styled-system/index.js`) : la prop `textStyle` est volontairement une prop de **remplissage** — `getWithPriority(theme, 'textStyles.<name>', styles)` n'applique une propriété du token QUE SI cette propriété n'est pas déjà présente dans l'objet de styles fusionné au moment où `textStyle` est traité. Pour tout composant qui a son propre `baseStyle`/`sizes`/`defaultProps.size` dans son theme component Chakra (ex. `Heading` → défaut Chakra non surchargé : `fontFamily`, `fontWeight: 'bold'`, `size` par défaut `'xl'` → `fontSize`/`lineHeight` responsive déjà fixés AVANT que `textStyle` soit évalué), ces propriétés (`fontFamily`, `fontWeight`, `fontSize`, `lineHeight`) sont donc TOUJOURS déjà "présentes" → `textStyle` ne les écrase jamais, silencieusement, sans warning. Seules les propriétés absentes du baseStyle du composant (ex. `letterSpacing`, `textTransform`, `maxW`) passent. Même mécanique pour `ModalHeader` (part `header` du thème `Modal` : `fontSize: 'xl'`, `fontWeight: 'semibold'` en baseStyle).
  - **Solution retenue (ciblée, pas de fix global théorique risqué)** : remplacer `Heading` par `Text as={tag}` partout où `textStyle` doit piloter `fontSize`/`fontFamily`/`fontWeight`/`lineHeight` — `Text` n'a aucun `baseStyle`/`sizes`/`defaultProps` dans `config/theme.ts` (seulement `variants: textVariants`, identique à `Heading`), donc rien ne bloque `textStyle`. Pour `ModalHeader` (usage unique dans tout le projet, dans `SkillSetModal.tsx`) : gardé `ModalHeader` tel quel (padding + accessibilité/aria-labelledby du `Modal` inchangés) mais le texte est maintenant niché dans un `<Text as="h2" textStyle="subtitle">` interne — `ModalHeader` ne porte plus `textStyle` lui-même.
  - Appliqué dans `components/Sidebar/index.tsx` (hero/title/label), `components/Sections/About/Detail.tsx` (title), `components/Sections/About/SkillSetModal.tsx` (label sur `SkillList`, subtitle niché dans `ModalHeader`).
  - **Règle pour la suite (US-005 Experience, US-006 Projects, US-007 Contact)** : ne jamais poser `textStyle` directement sur un `Heading` ou tout composant Chakra ayant son propre `baseStyle`/`sizes`/`defaultProps` dans le thème (vérifier dans `config/theme.ts` section `components`, et dans le thème par défaut de Chakra si le composant n'y est pas listé) — toujours utiliser `Text as={tag}` (ou nicher un `Text`/`Box` interne) pour tout élément devant recevoir un `textStyle` de `config/theme.ts`. `Text`/`Box`/`Link`/`Button`(si on ajoute un jour un `textStyle` sur un bouton, vérifier d'abord que `Button` n'a pas de `fontSize` dans son propre `baseStyle` — il en a un par défaut dans Chakra, donc même piège potentiel) sont à vérifier au cas par cas.
  - **fontVariantCaps 'small-caps'** : ajouté directement dans les tokens `title` et `subtitle` de `textStyles` (`config/theme.ts`) plutôt que répété par composant — tout élément utilisant ces deux textStyles hérite automatiquement de la signature typographique des titres de section. Vérifié : n'entre pas en conflit avec `textTransform="uppercase"` passé en prop séparée sur "Solofomahery D."/"RAKOTONINDRINA" (le texte déjà transformé en majuscules par CSS n'a plus de minuscules à transformer en petites capitales, donc aucun effet visuel supplémentaire, pas de régression).

  - **Méthode de vérification `getComputedStyle` sans `mcp__playwright__*` chargé** (toujours absent de cette session malgré `.mcp.json` + redémarrage) : le CLI `npx playwright screenshot` (utilisé en US-003) ne permet pas d'exécuter du JS dans la page. Solution qui fonctionne : localiser le package `playwright` déjà mis en cache par un `npx` précédent (`$(npm config get cache)/_npx/<hash>/node_modules/playwright` — plusieurs hash possibles, vérifier lequel contient un `package.json` avec une version dont le navigateur correspondant est déjà présent dans `%LOCALAPPDATA%\ms-playwright\` ; ici `chromium-1248` était installé donc le hash avec `playwright@1.64.1` a marché, pas celui avec une version alpha plus récente qui demandait `chromium_headless_shell-1252` absent), puis `require()` ce chemin absolu depuis un script Node classique (`.cjs`) dans le scratchpad. Permet `page.evaluate(() => getComputedStyle(...))`, capture d'écran, lecture de `scrollWidth`/`clientWidth` (test no-horizontal-overflow) et listeners `console`/`pageerror` (détection d'erreurs React), le tout sans dépendre du serveur MCP. Résultat appliqué ici : `textStyle="title"`/`"subtitle"` confirmés appliqués (36px/600/small-caps et 24px/500/small-caps à 1440px, 30px/20px à 375px) — pas de régression du bug Heading/textStyle, confirmant que la règle "toujours `Text as={tag}`, jamais `Heading`" tient pour une nouvelle section.

## Pièges connus
- `mcp__playwright__*` non chargé dans certaines sessions même si déclaré dans `.mcp.json` et dans les `tools:` de l'agent — nécessite un redémarrage de Claude Code. Toujours absent lors de l'US-004 et du bugfix `textStyle` post-US-004. Si absent, le signaler explicitement plutôt que de deviner un rendu (vérifié ici via `curl` sur le HTML SSR + inspection des `<style data-emotion>` générés — technique fiable pour lire les règles CSS calculées réelles sans navigateur : chercher la classe `css-xxxxxx` de l'élément dans le HTML SSR, puis chercher `.css-xxxxxx{...}` dans les balises `<style>` injectées par emotion — mais ça ne remplace pas une vérification visuelle réelle, notamment pour le `SkillSetModal` qui n'existe qu'en state client, donc invisible en SSR/`curl`).
- Pour vérifier la convention de nommage des variables CSS générées par les semantic tokens Chakra sans navigateur : `toCSSVar()` de `@chakra-ui/styled-system` sur un thème minimal reproduisant les tokens concernés (testé en Node direct, rapide et fiable).
- `Stack w="100"` dans `Sidebar` (pré-existant, pas touché) : `"100"` n'est pas une clé valide de l'échelle `sizes` Chakra → valeur CSS littérale invalide, ignorée par le navigateur. Bug pré-existant hors scope US-003, à corriger si une tâche future touche ce `Stack`.
