- **Bugfix post US-003/US-004 : `textStyle` sans effet sur `Heading`/`ModalHeader`** — cause racine identifiée en lisant le code source de `@chakra-ui/system`/`@chakra-ui/styled-system` (`toCSSObject` dans `system.js`, `getWithPriority` dans `styled-system/index.js`) : la prop `textStyle` est volontairement une prop de **remplissage** — `getWithPriority(theme, 'textStyles.<name>', styles)` n'applique une propriété du token QUE SI cette propriété n'est pas déjà présente dans l'objet de styles fusionné au moment où `textStyle` est traité. Pour tout composant qui a son propre `baseStyle`/`sizes`/`defaultProps.size` dans son theme component Chakra (ex. `Heading` → défaut Chakra non surchargé : `fontFamily`, `fontWeight: 'bold'`, `size` par défaut `'xl'` → `fontSize`/`lineHeight` responsive déjà fixés AVANT que `textStyle` soit évalué), ces propriétés (`fontFamily`, `fontWeight`, `fontSize`, `lineHeight`) sont donc TOUJOURS déjà "présentes" → `textStyle` ne les écrase jamais, silencieusement, sans warning. Seules les propriétés absentes du baseStyle du composant (ex. `letterSpacing`, `textTransform`, `maxW`) passent. Même mécanique pour `ModalHeader` (part `header` du thème `Modal` : `fontSize: 'xl'`, `fontWeight: 'semibold'` en baseStyle).
  - **Solution retenue (ciblée, pas de fix global théorique risqué)** : remplacer `Heading` par `Text as={tag}` partout où `textStyle` doit piloter `fontSize`/`fontFamily`/`fontWeight`/`lineHeight` — `Text` n'a aucun `baseStyle`/`sizes`/`defaultProps` dans `config/theme.ts` (seulement `variants: textVariants`, identique à `Heading`), donc rien ne bloque `textStyle`. Pour `ModalHeader` (usage unique dans tout le projet, dans `SkillSetModal.tsx`) : gardé `ModalHeader` tel quel (padding + accessibilité/aria-labelledby du `Modal` inchangés) mais le texte est maintenant niché dans un `<Text as="h2" textStyle="subtitle">` interne — `ModalHeader` ne porte plus `textStyle` lui-même.
  - Appliqué dans `components/Sidebar/index.tsx` (hero/title/label), `components/Sections/About/Detail.tsx` (title), `components/Sections/About/SkillSetModal.tsx` (label sur `SkillList`, subtitle niché dans `ModalHeader`).
  - **Règle pour la suite (US-005 Experience, US-006 Projects, US-007 Contact)** : ne jamais poser `textStyle` directement sur un `Heading` ou tout composant Chakra ayant son propre `baseStyle`/`sizes`/`defaultProps` dans le thème (vérifier dans `config/theme.ts` section `components`, et dans le thème par défaut de Chakra si le composant n'y est pas listé) — toujours utiliser `Text as={tag}` (ou nicher un `Text`/`Box` interne) pour tout élément devant recevoir un `textStyle` de `config/theme.ts`. `Text`/`Box`/`Link`/`Button`(si on ajoute un jour un `textStyle` sur un bouton, vérifier d'abord que `Button` n'a pas de `fontSize` dans son propre `baseStyle` — il en a un par défaut dans Chakra, donc même piège potentiel) sont à vérifier au cas par cas.
  - **fontVariantCaps 'small-caps'** : ajouté directement dans les tokens `title` et `subtitle` de `textStyles` (`config/theme.ts`) plutôt que répété par composant — tout élément utilisant ces deux textStyles hérite automatiquement de la signature typographique des titres de section. Diagnostiqué via `MutationObserver({childList:true, subtree:true, attributes:true})` sur le conteneur de section (`#contact` montait à ~180 mutations/s, contre 0 sur les autres sections) — symptôme concret en test Playwright : `locator.hover()` échoue avec "element is not stable"/"element was detached from the DOM, retrying" en boucle, hover globalement impossible à vérifier tant que le composant remonte sans arrêt. **Règle pour la suite** : toujours définir les `motion(X)` au niveau module (hors du corps de la fonction), surtout dès qu'un composant a son propre hook d'état (`useState`, `useInView`, etc.) — pas seulement par souci de perf (best practice React standard) mais parce que ça peut littéralement casser le composant. À vérifier/corriger si une future tâche touche à nouveau Sidebar/Detail/Experience/FeaturedWorks ET qu'on y ajoute un hook d'état local (le risque est resté latent mais inoffensif dans ces 4 fichiers tant qu'aucun hook d'état interne n'y re-render en boucle).

**Cohabitation des 3 systèmes de scroll (point le plus risqué de la proposition, confirmé faisable, risque réel mais bien documenté/maîtrisable)** :
- Lenis **ne fake pas le scroll via un `transform` sur un wrapper** (contrairement à locomotive-scroll) — il pilote le **vrai** scroll natif (`window.scrollY`/`scrollingElement.scrollTop`), juste amorti dans le temps. Confirmé par le README officiel : "Runs on native scroll — wraps the browser's own scroll, so `position: sticky`, anchor links, and accessibility keep working." Conséquence directe : `useScroll()`/`useTransform()` de Framer Motion (About, Experience, jauge HUD) **n'ont besoin d'aucun code de glue** — ils lisent la même position de scroll réelle que Lenis fait avancer, exactement comme ils le feraient sans Lenis. Idem pour `IntersectionObserver`/`react-intersection-observer` (déjà utilisé dans Skills/GetInTouch) : un observer ne dépend pas de la cadence des événements `scroll`, seulement de la position réelle de l'élément, donc aucun impact.
- GSAP ScrollTrigger a besoin d'une synchronisation explicite (son propre ticker interne, pas branché nativement sur l'event `scroll`) : pattern **officiellement documenté par Lenis lui-même** (README, section "GSAP ScrollTrigger"), à copier tel quel :
  ```js
  lenis.on('scroll', ScrollTrigger.update)
  gsap.ticker.add((time) => { lenis.raf(time * 1000) })
  gsap.ticker.lagSmoothing(0)
  ```
  Donc : pas "3 moteurs qui se marchent dessus" mais **1 moteur (Lenis) qui pilote le scroll réel + 2 lecteurs passifs** (Framer Motion sans rien faire, GSAP avec ce snippet officiel). Architecture saine, pattern très répandu (sites "awwwards"-style), pas une expérimentation risquée.
- Pièges d'implémentation à ne pas rater (pas des blocages, mais à faire correctement) :
  - Ne pas cumuler l'amorti Lenis (`lerp`) ET un `scrub` GSAP avec sa propre inertie supplémentaire → sensation "molle"/double-lissée. Garder le scrub GSAP en valeur numérique directe (pas de smoothing GSAP additionnel), Lenis gère déjà l'amorti.
  - Ne jamais utiliser `ScrollTrigger.normalizeScroll()` en même temps que Lenis (les deux veulent "posséder" la normalisation du scroll → conflit direct, non documenté dans la proposition, à surveiller en implémentation).
  - **Lenis ne supporte pas CSS `scroll-snap` sur l'axe qu'il pilote** ("no support for CSS scroll-snap, you must use lenis/snap" — limitation officielle). La galerie Projects mobile (section 6, `scroll-snap-type: x` natif) est un conteneur **imbriqué**, axe horizontal différent de l'axe vertical piloté par Lenis — doit être explicitement exempté de l'écoute wheel/touch de Lenis via l'attribut `data-lenis-prevent` (ou `data-lenis-prevent-touch`/`-horizontal`) posé sur ce conteneur, sinon Lenis risque d'intercepter le swipe et de perturber le scroll-snap natif. Pas dans la proposition actuelle — ajustement à prévoir à l'implémentation.
  - Limitation Lenis documentée directement pertinente ici : *"position fixed seems to lag on MacOS Safari pre-M1"* — la Sidebar du site est `position: fixed` sur desktop (US-003). À tester explicitement sur Safari/macOS pendant l'implémentation (pas seulement Chrome/Firefox).
- **Ancres du Menu (`#aboutMe`, `#jobs`, `#works`, `#contact`)** : Lenis a un support natif intégré, pas besoin de réécrire les handlers `onClick` existants — option `anchors: true` (ou `{ anchors: { offset, onComplete } }`) à l'initialisation intercepte tous les clics sur `<a href="#...">` et appelle `lenis.scrollTo()` automatiquement. Risque de régression sur `components/Menu` plus faible que redouté par la proposition : pas de réécriture individuelle de chaque lien, une seule option globale. À vérifier quand même en Playwright réel après activation (comportement already testé/validé en US-008/US-010, ne doit pas changer).
- **Reduced motion** : Lenis respecte `prefers-reduced-motion` **nativement et par défaut** (`respectReducedMotion: true` déjà activé par défaut) — désactive l'amorti (`lerp` forcé à 1) et rend les `scrollTo`/clics d'ancre instantanés, sans code de détection custom à écrire pour Lenis lui-même. Reste à gérer séparément : désactiver/adapter les effets qui *dépendent* de Lenis (jauge HUD, pin GSAP) sous ce mode, comme déjà prévu par la proposition — Lenis ne le fait pas à leur place.

  - **#2 Piège de focus** : `Tab` continuait vers `#mainGrid` (contenu principal, `pages/index.tsx`) sous l'overlay menu mobile ouvert. Fix : `useEffect` dans `Navigation.tsx` qui pose/retire l'attribut natif `inert` sur `document.getElementById('mainGrid')` selon `isMobile && isOpen` (pas de nouvelle dépendance, pas de `FocusLock`). **Décision technique** : accès direct via `document.getElementById` plutôt qu'un state/context levé jusqu'à `pages/index.tsx` — `Menu`/`Navigation` et `#mainGrid` sont des *siblings* dans l'arbre (pas parent/enfant), lever l'état jusqu'à la page aurait été disproportionné pour ce fix ciblé. `setAttribute('inert', '')`/`removeAttribute('inert')` utilisés plutôt que la prop JSX `inert` (évite tout risque de typage avec `@types/react` 17.0.15, qui ne reconnaît pas forcément `inert` comme prop JSX valide ni son sérialisé booléen correct — `setAttribute` avec une string vide est sans ambiguïté, un attribut HTML booléen n'a que sa *présence* qui compte, pas sa valeur).

  - **#5 "CSS mort" `.blogBtn`/`textDecoration="none"` — investigué, PAS de changement fait (décision justifiée)** : vérifié par `getComputedStyle` réel (hover ET focus simulés, pas juste lu le CSS) que `.blogBtn:hover`/`.blogBtn:focus` (`styles.module.css`) l'emportent bel et bien sur `textDecoration="none"` du `Link` — `text-decoration-line` mesuré passe de `none` (repos) à `underline` (hover/focus).
