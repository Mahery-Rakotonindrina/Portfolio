## Procédure de test établie
- `npm run lint` et `npx tsc --noEmit` doivent passer (ne PAS lancer `npm run build` si le serveur dev tourne déjà sur le port 3000 — ça corrompt son cache `.next`. Vérifier d'abord `curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/` avant de relancer quoi que ce soit).
- `mcp__playwright__*` n'a pas été chargé dans la session tester lors d'US-009 malgré `.mcp.json` + redémarrage antérieur (même limite déjà documentée côté developer) — contournement utilisé avec succès : script Node (`.cjs`) qui `require()` directement le package `playwright` mis en cache par un `npx` précédent (chemin Windows avec slashes `C:/Users/.../_npx/<hash>/node_modules/playwright`, jamais le style `/c/Users/...` : ce dernier casse `require()` sous Node Windows natif même si `ls`/`cat` bash l'acceptent très bien). Hash qui a fonctionné ici : `e41f203b7505f1fb` -> `playwright@1.64.1`, compatible avec `chromium-1248` deja installe.
- Piège méthodologique important (nouveau, decouvert en US-009) : un `page.screenshot({ fullPage: true })` pris juste apres `page.goto()` sans scroll reel donne un faux negatif de "page vide" pour toute section qui utilise `whileInView`/`viewport={once:true}` (Framer Motion) -- ces sections restent a `opacity:0` tant que l'IntersectionObserver ne les a pas vues defiler dans le viewport reel, donc un simple chargement + capture plein format les montre vides/transparentes alors qu'elles sont parfaitement fonctionnelles pour un vrai utilisateur qui scrolle. Toujours scroller programmatiquement par paliers (`window.scrollTo` par pas de ~300px avec `waitForTimeout` entre chaque) jusqu'en bas puis revenir en haut avant une capture `fullPage`, sinon on rapporte des faux bugs.
- Deuxieme piege methodologique (US-009) : `page.screenshot({ fullPage: true })` ne gere PAS correctement les elements `position: fixed` (ex. `Sidebar` passe en `position: fixed` au breakpoint `xl`, `components/Sidebar/index.tsx:47`) -- la capture plein format les fait disparaitre entierement de l'image composite, alors qu'un screenshot de viewport simple (`page.screenshot()` sans `fullPage`) apres un `scrollTo` montre bien le Sidebar fixe correctement affiche a cote du contenu qui defile. Si une section semble "manquante" uniquement en capture `fullPage` a partir d'un breakpoint donne, toujours revérifier avec un screenshot de viewport simple avant de conclure a un bug.
- Pour lire un rapport JSON Playwright trop volumineux (stack traces React completes dans les warnings console), utiliser Grep cible sur les cles utiles (`hasOverflow`, `pageErrors`, etc.) plutot que Read brut.
- Filtrer des la collecte des listeners `console` les warnings deja documentes comme hors-scope (`boxSize`, `marginBottom`, `isDarkMode` -- Avatar/toggle) pour ne pas se noyer dans du bruit connu a chaque run.
- Ecriture de scripts `.cjs` multi-lignes via `cat >> fichier <<'EOF'` dans Bash : un tres gros bloc unique (~150 lignes) a provoque une erreur `unexpected EOF while looking for matching` plusieurs fois, meme sur ce fichier de memoire, sans cause isolee precisement (ni accents ni backticks seuls ne la reproduisent). Toujours decouper un heredoc volumineux en plusieurs `cat >>` successifs plus petits plutot que chercher la cause exacte.
- `page.locator('text=A, text=B')` n'est PAS une syntaxe OR valide Playwright -- utiliser `page.getByText(/regex/i)` pour un texte avec apostrophe/accent qui pourrait varier legerement.

## Zones fragiles connues
- Chevauchement visuel menu mobile/tablette (liens "A PROPOS"/"EXPERIENCES"/"REALISATIONS"/"CONTACT") avec le texte du Sidebar derriere, a 375px ET 768px, clair ET sombre. Le fond du menu mobile (`components/Menu/Navigation.tsx`, `bg = rgba(11,13,18,0.9)` dark / `rgba(237,242,247,0.95)` light) est volontairement translucide (US-008), donc le texte du Sidebar reste visible-mais-dimmed derriere les liens de nav, creant un chevauchement de texte bien reel (ex. "A PROPOS" superpose pile sur "...voir ici, Merci beaucoup!"). Confirme stable apres 900ms (pas un artefact d'animation en cours) et confirme deja present a l'identique dans `screenshots/us008-menu-mobile-dark-open.png` (donc pre-existant depuis US-008, pas une regression de cette passe) -- mais jamais signale comme probleme de lisibilite jusqu'ici.
- Breakpoint tablette (768px) = `md` Chakra exactement : `pages/index.tsx` ne bascule le `Grid` en colonnes cote a cote (`Sidebar` + contenu) qu'a partir de `lg` (992px) -- donc a 768px tout est empile en une seule colonne verticale, comme en mobile. Choix de layout intentionnel, pas un bug, mais a garder en tete pour toute future tache touchant au Grid : 768-991px a le layout "empile", pas "deux colonnes".
- `Sidebar` passe en `position: fixed` uniquement a `xl` (1280px+) -- seul breakpoint ou le Sidebar reste visible pendant que le reste defile ; en dessous (y compris tablette 768px) il defile avec le contenu car empile au-dessus.
- Boutons tactiles (`Color Mode` 40x40, hamburger `MenuToggle` 40x40) sous le seuil AAA recommande de 44x44 mais au-dessus du minimum AA (24x24, WCAG 2.2) -- fonctionnels, cliques sans probleme en test, pas remonte comme bug mais a garder a l'oeil si une tache d'accessibilite dediee est lancee un jour.

## US-010 — Accessibilité (2026-11-05) : méthode et résultat

### Méthode ajoutée à la procédure établie
- `npx @axe-core/cli` en CLI direct échoue sur cette machine (ChromeDriver 152 vs Chrome 156 installé réellement, mismatch de version non corrigible sans `browser-driver-manager install chrome`, pas tenté — pas nécessaire). Contournement qui fonctionne : charger `axe-core` (le package, pas le CLI) directement en JS via le même contournement `require()` du `playwright` mis en cache, injecter `axe.min.js` dans la page via `page.addScriptTag({content: ...})` puis `window.axe.run(document, {runOnly:{type:'tag', values:['wcag2a','wcag2aa','wcag21aa']}})`. Binaire `axe-core` déjà présent dans le cache `_npx` (ex. hash `548ec2e7c8d2ddd8/node_modules/axe-core/axe.min.js`) — chercher avant de réinstaller.
- **Piège méthodologique important (nouveau)** : un audit `axe-core` lancé juste après un scroll programmatique (même avec un `waitForTimeout` court, ~400ms) peut capturer un élément **mid-transition** (`whileInView`/`AnimatePresence` pas encore stabilisé) et rapporter un `color-contrast` en échec alors que le rendu stabilisé est parfaitement conforme — axe calcule la couleur "effective" en tenant compte de l'opacité des ancêtres, donc un élément en fondu à opacité 0.3 ressort avec une couleur "mélangée" proche du fond, donnant un ratio artificiellement catastrophique (ex. 1.1:1 au lieu de 7.14:1 une fois stabilisé). Observé concrètement sur `ScrollMore` (lien email flottant bas-droite, apparaît en scrollant) et sur le texte accentué de `About/Detail.tsx` ("thé"/"la gestion de logiques métier côté client") lors d'un premier run mal contrôlé. **Toujours** laisser un vrai délai de stabilisation (≥1.5s) après le dernier scroll et avant de lancer `axe.run()`, ou mieux : scroller l'élément cible précisément en vue (`scrollIntoView`) et attendre, plutôt qu'un simple `scrollTo` global suivi d'un retour en haut de page. Un run "propre" (longs paliers de scroll + 1.8s de stabilisation avant audit) donne un résultat totalement différent (quasi aucune violation) d'un run pressé sur la même page — ne jamais conclure à un bug de contraste sur un seul run si l'élément concerné est animé par `whileInView`/`AnimatePresence`.
- Pour auditer le focus clavier réel (pas une supposition de lecture de code) : `page.keyboard.press('Tab')` + `getComputedStyle(document.activeElement).boxShadow` **avec un `waitForTimeout(~300ms)` après chaque Tab** — sans ce délai, Chakra/Framer n'ont pas fini la transition et le `boxShadow` lu est encore transparent (faux négatif "pas de focus visible" alors qu'il apparaît correctement 300ms plus tard). Le piège inverse existe aussi : cliquer au préalable avec la souris (même sur un élément sans rapport, ex. pour changer de thème) puis appeler `.focus()` par programme sur un autre élément ne déclenche PAS `:focus-visible` dans Chromium (heuristique "dernière modalité d'interaction" posée à "pointeur") — ne jamais mélanger clic souris + `.focus()` programmatique dans un même test de focus clavier ; utiliser uniquement `page.keyboard.press('Tab')`/`Enter`/`Espace` de bout en bout pour un test représentatif d'un vrai utilisateur clavier.

### Bugs trouvés (US-010, classés par gravité) — non corrigés, rapportés au PO
1. **Majeur** — Bouton hamburger du menu mobile (`components/Menu/toggle.tsx`, `MenuToggle`) sans `aria-label` (ni `aria-expanded`/`aria-controls`) : un `<button>` natif contenant seulement un `<svg>` sans nom accessible. Un utilisateur de lecteur d'écran n'a aucune indication du rôle/état de ce contrôle. Confirmé par lecture du DOM réel (`outerHTML`) à 375px.
2. **Moyen** — Le menu mobile ouvert (`components/Menu/Navigation.tsx` + `index.tsx`) n'a pas de piège de focus : après les 4 liens de nav, `Tab` continue vers des liens situés plus bas dans la page (`mail`, `Designed and Made with` de `GetInTouch`), visuellement masqués sous l'overlay opaque du menu mais toujours dans l'ordre de tabulation — confirmé par script (positions DOM identiques, `offsetParent !== null`). Normal : ce n'est pas un `Modal`/`Drawer` Chakra (pas de `role="dialog"`/`FocusLock` automatique), donc pas de piège par défaut — mais le comportement reste déroutant pour un utilisateur clavier.
3. **Moyen** — `Escape` ne ferme pas le menu mobile ouvert (confirmé : position du lien "Contact" strictement identique avant/après `Escape`). Seul un nouvel `Enter`/`Espace` sur le bouton hamburger (qui garde le focus après l'ouverture) referme le menu — donc pas de piège au sens strict (il existe un chemin clavier pour refermer), mais `Escape` est la convention quasi universelle pour les overlays plein écran et son absence est une vraie lacune UX.
4. **Mineur** — `components/Sections/GetInTouch/index.tsx` : le lien inline "mail" dans le paragraphe ne se distingue du texte environnant que par la couleur (`accent.default` vs `text.secondary`), sans soulignement ni autre style — contraste insuffisant entre le lien et le texte voisin (1.2:1 dark / 1.82:1 light, seuil WCAG 1.4.1 "Use of Color" = 3:1). Trouvé par `axe-core` (règle `link-in-text-block`), confirmé stable sur un run bien contrôlé (pas un artefact transitoire), dans les deux thèmes. Capture `screenshots/us010-getintouch-maillink-dark.png`.
5. **Mineur / dette de code, pas un blocage WCAG** — Les 4 liens de nav principaux (`components/Menu/Navigation.tsx`, classe `styles.blogBtn`) ont un indicateur de focus clavier **différent** du reste du site (changement de couleur `text.secondary` → `accent.default` au lieu du halo `box-shadow` générique Chakra utilisé partout ailleurs) à cause d'un `_focusVisible={{ boxShadow: 'none', ... }}` explicite sur le `Link` + `.blogBtn { box-shadow: none !important; }` dans `styles.module.css`. Le changement de couleur reste réellement visible (confirmé par capture d'écran avant/après `Tab`, clair et sombre — `screenshots/us010-nav-focus-*-dark.png`/`-light.png`) donc ce n'est PAS un échec WCAG 2.4.7 en soi. Mais le soulignement prévu pour accompagner ce changement (`.blogBtn:hover/:focus { text-decoration-color: accent }` dans le CSS module) ne s'affiche jamais : le `Link` porte aussi `textDecoration="none"` (prop Chakra), qui fixe `text-decoration-line: none` et neutralise totalement l'effet de la couleur de soulignement (code mort, confirmé par `getComputedStyle().textDecorationLine === 'none'` même en focus). Vraisemblablement un oubli de nettoyage lors d'une migration passée (US-008) plutôt qu'un choix voulu.

### Points vérifiés OK (US-010)
- **Contrastes** : aucune violation `color-contrast` réelle (hors artefacts transitoires expliqués ci-dessus) sur l'ensemble du DOM, clair et sombre, une fois les animations stabilisées — confirmé par `axe-core` sur la page complète ET par calcul manuel WCAG sur des éléments concrets (texte accentué About, CTA "Mon attirail de développeur" : 7.14:1 dark / 5.82:1 light, exactement les valeurs calculées par le designer en US-002).
- **Alt text** : les 8 `<img>` du site (photo de profil + 3 logos d'entreprise Experience + 4 images de projets FeaturedWorks, modal de compétences inclus) ont toutes un `alt` non vide et pertinent (nom de la personne/entreprise/projet). Aucune icône de compétence n'est un `<img>` (toutes en SVG inline `react-icons`, décoratives, toujours accompagnées d'un libellé texte visible à côté) — pas de alt à ajouter.
- **Navigation clavier (reste)** : ordre de tabulation logique de bout en bout (14 éléments interactifs réels sur toute la page, aucun "trou" ni élément interactif visuellement présent mais non atteignable). Halo de focus Chakra par défaut (bleu générique `#4299E1`, pas la couleur accent du projet — `shadows.outline` jamais surchargé, cf. `.claude/memory/designer.md`) bien visible dans les deux thèmes sur tous les liens/boutons sauf la nav (cf. finding 5). Modal de compétences : ouverture au clavier (`Tab` + `Enter` sur "Mon attirail de développeur"), focus piégé à l'intérieur (vérifié sur 6 `Tab` consécutifs, jamais sorti), `Escape` ferme et rend le focus au bouton déclencheur — comportement standard `Modal` Chakra, aucun bug. Hamburger mobile activable par `Enter` ET `Espace` (bouton natif).

### Zone fragile à surveiller la prochaine fois
- `components/Menu/toggle.tsx` (`MenuToggle`) et le piège de focus du menu mobile (`Navigation.tsx`/`index.tsx`) : si une future tâche touche au menu mobile, vérifier que ces 3 points (aria-label, piège de focus, Escape) ont bien été traités avant de les considérer résolus.

## US-021 — QA Phase 2 (2026-11-05) : methode et resultat

### Bug critique trouve (non corrige, rapporte au PO)
- **`npm run build` échoue réellement** : `components/Sections/GetInTouch/WireframeShape.tsx:48` — `react/no-unknown-property` sur la prop `transparent` de `<meshBasicMaterial>` (R3F, US-019). `.eslintrc` n'autorise que `wireframe` dans l'allowlist de cette règle (ajoutée en US-019), jamais `transparent`.
- **Piège d'environnement majeur découvert ici, à ne jamais reperdre : `npm run lint` (`next lint`) peut rapporter un faux "No ESLint warnings or errors" à cause d'un cache obsolète `.next/cache/eslint`.** Confirmé en conditions contrôlées : `npm run lint` passait (faux), `rm -rf .next/cache/eslint` puis `npm run lint` à nouveau échoue avec la même erreur que `npm run build`, de façon parfaitement reproductible (`npx eslint <fichier>` direct confirme aussi l'échec). **Toujours supprimer `.next/cache/eslint` avant un `npm run lint` de vérification finale**, sinon un fichier dont le cache est resté stale peut passer inaperçu indéfiniment. Très probablement déjà trompeur depuis US-019 — les "`npm run lint` passe" rapportés en US-019/US-020 étaient vraisemblablement déjà des faux positifs.

### Piege d'environnement de test majeur (contamination dev/prod), a ne jamais reproduire
- **Un `taskkill //F //PID <pid>` ciblé sur le PID reporté par `netstat` pour le port 3000 ne tue PAS forcément tout l'arbre de processus d'un `npm run dev` lancé en arrière-plan.** `npm run dev` en nohup crée une chaîne de process (`npm` → `next dev` → un worker qui bind effectivement le port, PID qui peut changer après un rechargement interne de Next). Tuer uniquement le PID du moment libère le port un court instant, mais le reste de l'arbre peut RECRÉER un nouveau worker qui re-bind le port 3000 juste après — y compris pendant qu'un `npm run build`/`next start` tourne en parallèle, corrompant `.next` (le process dev continue d'y écrire par-dessus un build de prod fraîchement généré). Symptôme observé : `next start` semblait avoir démarré correctement (log "Ready in 880ms" + warning `sharp` typiques de prod) mais le HTML/JS réellement servi portait les signatures du mode dev (chunks non hashés `_app.js`, absence de `.next/BUILD_ID`, stack traces avec `ReactDevOverlay`). Le PID qui écoutait réellement le port 3000 était un enfant de l'arbre `next dev` resté vivant, pas le process `next start` nouvellement lancé.
- **Toujours vérifier, avant de faire confiance à un serveur "prod" lancé pour un test de perf (Lighthouse) ou autre** : `powershell -Command "Get-CimInstance Win32_Process -Filter \"Name='node.exe'\" | Select ProcessId,ParentProcessId,CommandLine"` pour repérer tout process `next dev`/`npm run dev` résiduel AVANT de lancer un build/start de prod, et après coup, confirmer que le PID qui écoute réellement le port 3000 (`netstat -ano | grep LISTENING`) a bien pour commandline `next start` (pas `next dev`), ET que le HTML servi référence des noms de chunk hashés (`curl http://localhost:3000/ | grep _app`) correspondant exactement à la sortie du dernier `next build`. Un simple `curl -s -o /dev/null -w "%{http_code}"` qui répond 200 NE SUFFIT PAS à garantir qu'on teste le bon build.
- Pour tuer proprement un arbre `npm run dev` lancé via nohup/disown sous Windows/Git Bash : `taskkill //F //PID <pid> //T` (`//T` = tree, tue toute la descendance) plutôt qu'un `taskkill //F //PID <pid>` simple sur le PID du worker de port.
- Les résultats Lighthouse mesurés avant et après le nettoyage de la contamination étaient en fait très proches (perf mobile 70 vs 71, desktop 86 vs 88) — la contamination n'a donc probablement pas faussé significativement les chiffres rapportés ici, mais ça reste un coup de chance, pas une garantie : toujours revérifier la propreté du build avant de prendre des mesures de perf comme définitives.

### Piege de test confirme (deja documente par le developer, revu ici dans un nouveau contexte)
- **`scrollIntoView()` sur une section après la galerie Projects (pin GSAP) pendant que Lenis est actif peut laisser apparaître un résidu visuel du dernier état pin (texte de la dernière carte affiché en haut de l'écran, superposé à la section suivante) — PAS un bug réel, un artefact du saut instantané qui désynchronise l'état interne de GSAP ScrollTrigger de la position réelle.** Reproduit une fois avec `document.getElementById('contact').scrollIntoView()` (le `pin-spacer`/`wrapper` de la galerie Projects restait affiché en haut du viewport, superposé au contenu Contact) ; revérifié avec un VRAI scroll (`page.mouse.wheel` répété via `mcp__playwright__browser_run_code_unsafe`) depuis le haut de page jusqu'en bas : aucun résidu, Contact parfaitement propre. Toujours utiliser un vrai scroll (wheel) plutôt que `scrollIntoView`/`scrollTo` instantané pour vérifier visuellement une section qui suit immédiatement une scène pin+scrub GSAP.

### Methode ajoutee a la procedure etablie
- Pour contourner le build cassé le temps de continuer les autres vérifications (perf, visuel) sans pouvoir corriger le code (tester = lecture seule) : `npx next build --no-lint` (flag natif de `next build`, ne modifie aucun fichier) donne un build de prod utilisable pour tout sauf la vérification du critère lint/build lui-même, qui reste listé comme échoué.
- Lighthouse CLI (`npx lighthouse <url> --output=json --chrome-flags="--headless=new" --only-categories=performance,accessibility,best-practices,seo`, + `--preset=desktop` pour la variante desktop) fonctionne directement sur cette machine sans contournement (contrairement à `@axe-core/cli`, cf. US-010) — le package `lighthouse` s'installe à la volée via `npx` sans erreur de version ChromeDriver. Lire les résultats via un script Node qui charge le JSON (`require('./rapport.json')`) plutôt que `cat`/`Read` brut (fichier volumineux).
- Pour lire l'« element render delay » détaillé du LCP (utile pour distinguer un problème réseau d'un délai d'affichage intentionnel/JS) : `audits['lcp-breakdown-insight'].details.items[0]` (sous-parties `timeToFirstByte`/`elementRenderDelay` en ms) — bien plus parlant que le seul chiffre LCP agrégé.

### Zone fragile a surveiller la prochaine fois
- `.eslintrc` → `react/no-unknown-property` → `ignore: ["wireframe"]` : toute nouvelle prop R3F/drei non standard ajoutée dans une future tâche doit être ajoutée explicitement à cette liste — et il faut vérifier avec `.next/cache/eslint` SUPPRIMÉ, pas avec un simple `npm run lint` qui peut mentir.
- Avant toute mesure de perf/Lighthouse future : toujours lister les process `node.exe` (`Get-CimInstance Win32_Process`) et confirmer l'absence de `next dev` résiduel avant de faire confiance à un `next start` lancé pour le test.
